# 재생 방식 기록 (새 사이트 만들 때 참고)

## 공통 점검 순서
1. 회차 화면 HTML에서 iframe(data-src/src), m3u8, 토큰 문자열부터 찾는다.
2. 웹뷰 없이 일반 요청만으로 되는지 먼저 시험한다. 되면 가장 빠르고 안정적이다.
3. 막히면 사용자가 준 실제 m3u8 주소와 회차 HTML을 기준으로 단계별 진단(항목명 한 줄씩)으로 어디서 끊기는지 찾는다.
4. 앱 40초 제한: 큰 페이지 전체 분석은 멈출 수 있다. 빠른 길(정해진 경로만 따라가기)을 먼저, 실패하면 기존 분석으로 넘긴다.
5. 해외 IP는 대부분 Cloudflare 403이라 직접 시험 불가. 모의 시험 후 사용자 확인으로 검증한다.

## 후후티비 (hoohootv483.xyz, 주소 자주 바뀜: hs, ht, hu, hv)
- 회차 화면 iframe: vid.jwpcdn.net/video/embed/<id>/1280x720/<id> (세션 없음)
- embed 응답 안에 creatorofvideo.com/play/<player_uuid> 포함
- play 화면 인라인 스크립트에 window._HLS_PLAYLIST_TOKEN = "<JWT>" (30분, 접속 IP /64 묶임)
- 영상: creatorofvideo.com/hls/<segment_uuid>/1080p.m3u8?token=<JWT>&t=0 (720p, 480p, 360p 대안)
- 재생목록 200, 키 없음, 조각은 photoq.com 확장자 없는 정상 MPEG-TS
- 조각 요청은 Referer=play 주소, Origin=creatorofvideo.com 필요
- 웹뷰는 불필요했다. 웹뷰 의심은 추정이었고 틀렸다.
- 작품 화면 og:image는 사이트 기본 로고. 실제 표지는 목록 카드 이미지(data-src)를 기억해서 쓴다.

## 짭플릭스 (zzap208.com, 주소 번호가 바뀜: zzap + 숫자 + .com)
- 목록 /mobile/vodlist.php?type_id_1=N&order_type=(빈|vod_hits), 검색 search.php?sfl=…&sop=and&keyword=, 작품 vodview.php?id=N. 후후티비와 같은 계열 CMS 모양.
- 회차 화면은 가끔 HTTP 202(본문 비어 있음, CloudFront 확인 화면)로 옴. 브라우저와 같은 머리글을 붙이고 점점 늦춰 최대 6번 재시도하면 열린다.
- 회차 화면 안 iframe: chaktt.php?url=<mp4 주소>. 이 mp4 는 직접 재생이 막혀 있다(403). 쓰지 말 것.
- 플레이어 화면(chaktt.php)은 Referer 가 작품(회차) 화면일 때만 열린다.
- 플레이어 화면에 phpsiteEc(암호문)와 phpsitekey(열쇠)가 있다. 풀기: base64 해독 → 열쇠 글자 반복 XOR → 다시 base64 해독 → https://wiselife.blog/hls/….m3u8?t&n&s 주소.
- 이 주소는 요청마다 새로 만들어지므로 재생 직전에 풀어야 한다(미리 저장해 두면 안 됨). 1순위로 쓴다.
- 영상 요청은 Referer 가 핵심이다. 플레이어 주소 / 사이트 주소 / 없음 세 가지로 앞 2바이트를 받아 열리는 것을 먼저 쓴다.
- 선호 화질은 첫 HLS 항목만 펼쳐서 고른다. 자동이면 원래 재생 그대로.
- 해외 IP 는 CloudFront 차단이라 휴대폰 결과로만 검증했다.

## 후후티비와 짭플릭스 공통 정리
- 둘 다 일반 요청만으로 재생된다(웹뷰 불필요).
- 둘 다 영상 주소를 재생 화면에서 그때그때 만든다(후후티비 = 토큰으로 조립, 짭플릭스 = 암호문 풀기). 주소·토큰을 저장하지 말고 재생 직전에 만들 것.
- 둘 다 조각·재생목록 요청에 Referer(필요하면 Origin)가 핵심.
- 주소가 자주 바뀌므로 정식판에는 주소 자동 따라가기(번호 큰 쪽 채택), 선호 화질, 인기/최신 탭 규칙, 📡/📝 줄을 같이 넣는다.

## 티비룸 (tvroom49.org, 주소 번호가 바뀜) - 순정 앱에서 재생 성공(2026-11-28)
- 재생목록 조각 551개, 이름이 segment_list_N.png, AES-128(IV 있음). 열쇠 응답은 220자로 가려진 JSON이다.
- 확장의 unscramble 로 16바이트 열쇠를 복원하면 첫 블록 복호가 0x47(TS)로 맞는다. 즉 복원은 옳았다.
- 문제: 순정 앱의 HLS 프록시(createHlsProxyUrl)는 열쇠를 바꿔 주지 못하고 가려진 열쇠를 그대로 재생기에 준다 → 끝없이 로딩. Glitch 전용 X-Hls-Key(열쇠 바꿔 넣기)는 순정에 없다.
- 성공 방식(열쇠 중계 서버): 확장이 재생목록·기준 주소·복원한 열쇠(hex 32자)를 중계 서버 POST /api/p 로 보내면, 서버가 조각 주소를 절대 주소로 바꾸고 #EXT-X-KEY 주소를 ../k/<id>(열쇠 16바이트)로 바꾼 재생목록을 준다. 확장은 그 재생목록 주소를 createHlsProxyUrl 에 넣는다. 조각은 Referer = 플레이어 출처(https://player.pongping.top/)로 연다.
- 조각 이름이 .png 라서 재생기(ffmpeg)가 주소를 그대로 받으면 거부한다. 반드시 createHlsProxyUrl 을 거쳐 이름을 가려야 한다(데이터 주소 재생목록은 실패).
- 중계 서버: 메모리만 쓰는 작은 Node 서버(1개 항목 6시간, 최대 300개, 본문 400KB, IP당 분당 60회). 서버가 재시작돼 데이터가 사라져도 확장이 재생마다 다시 올리므로 문제없다. 비밀값은 공개 코드에 넣을 수 없어 두지 않고 크기·형식 검사와 횟수 제한으로 막는다. 서버 코드는 개인 저장소 relay/server.js.
- 중계가 안 되면 기존(글리치) 방식으로 되돌아가는 대비를 둔다. 설정 "열쇠 중계 서버 주소"를 비우면 기본 서버를 쓴다.
- 인증(Cloudflare) 요청 줄이기: 주소 이동 확인은 하루 한 번, 처음부터 사이트가 받아 주는 방식(UA 없이)으로 요청.

## 티비위키 (tvwikiNN.net, 주소 번호가 바뀜)
- 회차 화면의 iframe[data-session1] 에서 재생 세션을 얻는 구조다.
- 순정 앱에서 안 되는 이유는 티비룸과 같은 열쇠 문제(Glitch 전용 X-Hls-Key 필요)로 추정한다. 티비룸의 열쇠 중계 방식이 적용될 수 있으나 아직 시험하지 않았다(추정).

## 야툰 영상
- 일반 요청으로 재생 성공(0.0.8). 정식판 공통 규칙(필터, 회차 정렬) 적용.

## 교훈
- 순정 앱에서 안 되는 열쇠·조각 문제는 확장 안에서 풀려 하지 말고, 중간에 서버를 두어 재생목록과 열쇠를 바꿔 주는 방법을 먼저 생각한다.
- 앱이 띄우는 인증(403) 알림은 확장이 사이트 메인으로 보내는 부가 확인 요청에서도 생긴다. 부가 요청은 드물게(하루 한 번) 보낸다.
- 추정으로 우회책을 쌓기 전에 사용자의 실제 HTML, m3u8을 받아 구조부터 확정한다.
- 진단 결과는 앱 오류 화면(약 4줄)이나 영상 항목명 한 줄씩으로 내보낸다.
- 재생 시간은 재생목록 확인 생략처럼 불필요한 요청을 줄여 단축한다.
